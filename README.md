# Product Engineering for DSH · 产品交付台

把产品想法、设计、开发、验证与发布准备放进 DeepSeek Harness。保留 Product Engineering 上游的 44 个技能、6 个技能包及配套资料，增加 DSH 原生工作台、持久化产品记录、证据与决策管理。

基于 [phuryn/product-engineering](https://github.com/phuryn/product-engineering)，固定版本 `bdb2389c7636f6615c37fd66dd8518986284ec01`，遵循 MIT 许可。此项目是社区移植，与 DeepSeek 或上游作者无官方从属关系。

## 适合谁

- 用 Coding Agent 开发产品，希望知道当前做到哪里、下一步做什么的独立开发者。
- 需要审阅方案、做产品决策、检查交付证据的产品经理和研发负责人。
- 已在 DSH 中工作，希望在同一入口调用产品、研发、交接与表达方法的人。

## 新增能力

| 能力 | 实际作用 |
| --- | --- |
| DSH 原生产品页 | 在侧边栏进入项目，查看发现、设计、构建、发布、增长五个阶段 |
| 从仓库导入产物 | 读取工作区内的 UTF-8 文件，同时保存正文和文件快照；可显式重新导入 |
| 产物与依据关联 | 把方案、PRD、评审和发布材料与来源、文件或运行记录关联 |
| 待决定事项 | 模型可以提出选项，用户在页面记录选择与理由 |
| 发布准备检查 | 缺少依据、未决定的问题和失效结果会显示为阻塞项 |
| 修改后重新检查 | 材料更新或快照文件变化后，旧的检查结论不会继续作为有效通过 |
| 阻塞项转修复任务 | 为每项发布阻塞列出需补齐的材料与验收条件，打开带上下文的原生会话草稿 |
| 44 个技能入口 | 按包、阶段搜索；通过 DSH 原生会话调用，不在页面伪造执行结果 |
| 本地数据与导出 | 当前 DSH profile 隔离保存，可导出 JSON 和 Markdown |

上游已经有提案、状态记录、交接和用户审阅页面。这次增强集中在原生集成、结构化持久化与可执行检查规则，并不把上游已有方法当成新发明。

## 安装

首个验证目标是 DSH `0.2.1-rc.2`，Node.js `^22.19.0 || >=24.0.0`。DSH 是预发布软件，其他版本需要重新验证。部分技能中的 Python 工具或外部 CLI 仍需要相应运行环境；插件不会自动安装这些服务或读取它们的凭据。

从交付的 `.tgz` 包安装，替换为实际文件的绝对路径：

```sh
dsh plugin --profile desktop add /absolute/path/dsh-product-engineering-0.2.0.tgz
```

Web 用户把 `desktop` 换成 `web`。安装后重新启动对应 DSH 窗口或进程。在插件配置中确认 `product-engineering` 已启用，然后从侧边栏进入“产品交付台”。安装是本地操作，不需要把项目数据上传给本插件的服务。

## 第一次使用

1. 在 DSH 中打开一个产品的工作目录。
2. 进入“产品交付台”，创建产品，选择对应工作区，填写标题与目标。
3. 打开技能库，从“从这里开始”或适合当前任务的技能进入原生会话。
4. 在产物编辑器中填写正文，或选择从文件导入并填写工作区内相对路径；需要选择的事项会留在决策区。
5. 发布准备检查中逐项查看证据与修复任务。需要补齐材料时打开任务草稿，完成后回工作台重新核查；导出 Markdown 交付报告。

也可以直接在会话的第一行输入：

```text
/pe-start-here 我已有一个插件原型，帮我确定下一步。
```

四个由用户主动启动的流程分别是 `/pe-start-here`、`/pe-ship-check`、`/pe-handover`、`/pe-retro`。其余 40 个技能支持模型按需调用。所有技能使用 `pe-` 前缀，避免与已有技能同名。

## 六个技能包

| 包 | 用途 |
| --- | --- |
| Product | 产品方向、竞品、用户群、价值主张与增长 |
| AI Shipping | 应用文档、测试推导、独立评审、静态检查与发布准备 |
| Agent Teams | 分工、任务简报与外部 Coding Agent 协作方法 |
| Agent Harness | 指令维护、状态记录、交接、复盘与执行环境 |
| App Stack | 应用架构、权限、环境、数据库、监控等专项方法 |
| Work Humanizer | 保留事实与个人表达的工作写作 |

完整条目见 `upstream/catalog.json`。来源清单、文件摘要和具体适配说明随包保留在 `upstream/` 下；每个技能的引用资料与脚本位于自己的目录。

## 结果如何解释

- 文件证据的“已记录文件快照”表示插件读取了工作区内该文件并保存内容摘要，不表示其内容正确。
- URL、命令结果或文字记录是提交者报告的信息；登记不会自动执行命令，也不表示插件独立复核了结果。
- 模型调用不能冒充用户确认决定或豁免检查。用户的判断记录与模型提供的材料分开保存。
- “发布准备完成”只描述已登记项目满足检查条件，不等于产品绝无缺陷，也不会自动部署或发布。
- 技能是否能完成某项任务，取决于当前 DSH 的模型、工具、授权及外部环境。缺少能力必须明确报告，不能把未执行写成通过。

## 数据与权限

项目数据保存在当前 profile 的 `product-engineering` 子目录，采用 SQLite。并发保存使用版本校验，旧页面不能静默覆盖新版本。模型工具只能访问创建会话时选择的工作目录对应的项目；切换执行目录不会扩大访问范围。可信本机用户页面可以选择当前 profile 的项目。外部远程身份不自动获得用户决策权限。

插件不自动提交代码、不自动部署、不发送消息、不配置第三方密钥。导出可能含你主动登记的项目内容，请按实际分享范围使用。

## 开发与验证

```sh
npm install
npm run build
npm test
npm run check:package
npm pack
```

客户端使用 DSH 的 React 和模块加载器；宿主依赖由 DSH 提供。SQLite 在部分 Node 版本中会产生实验性功能警告。

真实宿主、浏览器和独立测试的运行方法与结果见仓库 `docs/product-engineering-acceptance.md`。源代码检查、模拟模型集成测试、真实模型任务效果是不同层次的证据，报告分别记录，不混称。

## 已知限制

- 不承诺其他 DSH 版本或全部操作系统兼容。
- 工作台的阶段依次推进，设计前需要简报，构建前需要 PRD 或计划。小修复可以直接从技能库启动，不必走完工作台各阶段。
- 外部 Claude Code、Codex、Grok、数据库和托管平台的技能保留为可选集成指南；安装本插件不会取得这些产品的访问权限。
- 发布判断围绕已登记产物与依据；不能替代完整自动化测试、人工体验或真实用户研究。
- 文件导入是用户或会话明确发起的读取，不是后台双向同步。导入不会写回仓库，重新采集证据也不会自动通过检查。
- 文件导入只接受工作区内无软链接的 UTF-8 文本，正文最多 32,000 字符；文件快照最多 2 MiB。
- 修复任务来自已登记的阻塞项，不会自动扫描代码、执行测试或证明修复成功。
- 初版提供本地 JSON/Markdown 导出，不包含团队云端协作服务。
